# Monsoon for customers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn Monsoon from Vincent's single-passcode app into a multi-customer app where each firm signs in with a company code and personal passcode, and Monsoon works against that firm's own Supabase database and Claude key, held encrypted in a separate accounts database.

**Architecture:** A new accounts database (Supabase project `aiqjtpodocvzyizjsige`, us-east-1) holds customers, people, pipelines, setup links, sign-in attempts and an activity log; credentials are AES-256-GCM encrypted under `MONSOON_MASTER_KEY`. Every route resolves an `Account` (customer + person + pipelines) from a `v2` session cookie and gets its CRM connection and Claude client from that account only. Customers connect through a one-time setup link and a generated SQL script that creates a restricted `monsoon_app` login; Vincent manages customers with a `tsx` command-line tool.

**Tech Stack:** Next.js 15 (App Router, Node runtime), TypeScript, `pg`, `@anthropic-ai/sdk`, Node `crypto`, vitest + local Docker Postgres (`monsoon-test`, port 55433), `tsx` for the admin tool.

**Spec:** `docs/superpowers/specs/2026-11-13-monsoon-customers-design.md` (section 11 overrides earlier sections). Read it before starting any task.

## Global Constraints

- Work in a clean git worktree on branch `monsoon-customers` (the main checkout's untracked folders break `tsc`, `vitest` and `next build`). Run `docker start monsoon-test` before database tests.
- Never echo a credential, connection string, note text, question or contact data in a response, log line or thrown message. Log lines carry error class name, Postgres code (5 chars) and HTTP status only — the existing pattern.
- Accounts database: `MONSOON_ACCOUNTS_DATABASE_URL` (server); on Vincent's PC the admin tool reads `~/.quantcloud/monsoon-accounts.env` (`MONSOON_ACCOUNTS_DB_PASSWORD`, `MONSOON_ACCOUNTS_DB_REF=aiqjtpodocvzyizjsige`, `MONSOON_ACCOUNTS_DB_HOST=aws-1-us-east-1.pooler.supabase.com`, `MONSOON_ACCOUNTS_DB_PORT=6543`) and builds the URL with user `postgres.<ref>`.
- `MONSOON_MASTER_KEY`: 32 random bytes, base64. Exists only in Vercel settings and in test env stubs. The admin tool never reads it.
- Session cookie: `v2.<customer uuid>.<person uuid>.<session number>.<expiry>.<hmac>`, HttpOnly, Secure, SameSite=Strict, 180 days (`SESSION_SECONDS = 15552000`). `v1` refused.
- Sign-in limits: 5 failures / 15 min per (company code, network address) → that pair locked 15 min; 50 failures / 15 min per company code → code locked 15 min. Locked answer: `Wrong company code or passcode. Try again later.` (status 429). Wrong answer: `Wrong company code or passcode.` (401).
- CRM address guard: host must match `^[a-z0-9-]+\.pooler\.supabase\.com$`, port 6543 or 5432, TLS verified against `MONSOON_DB_CA_CERT`. Local hosts are allowed only when `MONSOON_ALLOW_LOCAL_DB=1` and `NODE_ENV !== "production"`.
- Customer pooler user is `monsoon_app.<project-ref>`; Monsoon builds `postgresql://monsoon_app.<ref>:<urlencoded password>@<host>:6543/postgres`. Project ref matches `^[a-z0-9]{20}$`.
- Restricted login grants (exactly): `SELECT` on every Monsoon table; `INSERT` on `orgs, people, members, touches, captures, owners`; `UPDATE` on `people, members, touches`. RLS policies `TO monsoon_app` only, `USING (true)` / `WITH CHECK (true)`, one per granted action per table.
- Models: a customer's `model` (default `claude-haiku-5-5`) is used for card reading, tidying, Ask and research. For customer code `quantcloud`, any model matching `/opus|fable/i` is refused. The env overrides `MONSOON_MODEL`, `MONSOON_ASK_MODEL`, `MONSOON_RESEARCH_MODEL` are removed.
- Setup links: valid 7 days, single use (consumed with `UPDATE ... WHERE used_at IS NULL RETURNING`), at most 10 attempts. Expired/used message: `This setup link has expired. Ask for a new one.`
- Passcodes: five random words from the EFF large wordlist joined by `-`, generated by the admin tool, never chosen. At most 50 people per customer. scrypt N=32768, r=8, p=1, 16-byte salt, 32-byte key, stored `s1.<salt b64url>.<hash b64url>`.
- Encrypted value format: `k1.<12-byte nonce b64url>.<ciphertext b64url>.<16-byte tag b64url>`, AAD = `<customer id>|<field>`; fields are `claude_key` and `pipeline:<pipeline id>`.
- Activity actions: `sign_in, capture, batch_save, tidy, ask, act_note, act_stage, act_details, act_research, research, setup, replace`. Never contact data, note text or questions.
- No code ever deletes from a CRM. The only delete in accounts code is pruning `sign_in_attempts` older than 30 days.
- Vincent's production sign-in must never be broken between deploys (rollout order in Task 15).

## Review Focus

1. A person signed in to customer A sends a request naming a pipeline key that only customer B has (or a proposal signed during a B session) — expect 400 `Unknown estate` / 403 `This change has expired. Ask again.`, and B's database is never connected. Pinned in Task 9.
2. A customer revokes access (drops `monsoon_app` or changes its password) — the pipeline shows as unavailable in the selector and every route answers 502 `Could not reach the <label> CRM`, never a 500 or a leaked error. Pinned in Task 8 (estates route).
3. Two setup submissions for one link race — exactly one stores credentials; the other gets the expired message. Pinned in Task 11.
4. Vincent's account after the bootstrap: his existing passcode still works and both pipelines behave exactly as before, notes still written with `VF`. Pinned in Task 14.
5. A suspended customer or a person whose passcode was reset keeps an old cookie — refused within 60 seconds (cache) with 401, and the app returns to the sign-in screen. Pinned in Task 6.
